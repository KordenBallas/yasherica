## Findings

### F1 — P0 · PvE ↔ Arena combat controller parallel implementation

**What.** `CombatController` (`Scripts/Combat/Controller/CombatController.cs:20`, 388 lines) and `ArenaCombatController` (`Scripts/Combat/Arena/ArenaCombatController.cs:26`, 437 lines) both implement `ICombatController` and share **zero** code. Method bodies are verbatim copies with lockstep-networking edits layered into one of them:

- `AddUnit` — `CombatController.cs:112–148` vs `ArenaCombatController.cs:148–177` (identical modulo log prefixes);
- `InitializeBattlefield` — `CombatController.cs:363–376` vs `ArenaCombatController.cs:412–424` (identical);
- parallel `StartRound` / `EndRound` / `SetRoundPhase` / `CheckWinConditions` / `ResolveNextEnemyIntent` structures.

35 files reference `ICombatController`.

**Rule / cost.** §11 (duplication), §14 (the *same job done twice* — the brief's named dual-path hazard "PvE vs Arena combat paths"). Every combat-core change — Track K speed initiative, P3-11/P3-12 displacement and ring-push, status-effect wiring — must be implemented and unit-tested **twice**, or Arena silently keeps the old rule. That is the D6/D8 class of bug reproduced at controller level, and Track K is queued next.

**Reconvergence.** Extract the shared round/state core into one engine used by both (composition, not inheritance-for-reuse): unit-list mutation, battlefield lifecycle, phase sequencing as the shared part; round-lead policy (`RoundLeadPolicy`), resolution order (the `IArenaResolutionOrder` seam already exists), and the commit source (local planner vs network bundle) as injected strategies. **Cost:** ~10–15 files, compiler needed, arena determinism re-verification (the round-hash instrumentation in `ArenaCombatController.cs:96` is the safety net). **Disposition:** ROADMAP — schedule **before** Track K adds more combat depth.

### F2 — P0 · `PlatformRegistry` is a static singleton service locator

**What.** `Scripts/Platform/View/PlatformRegistry.cs:13–26` — a `MonoBehaviour` that lazily **creates itself** (`new GameObject` + `AddComponent` + `DontDestroyOnLoad`) behind a static `Instance` property. Consumed as a locator at:

- `Scripts/Character/CharacterMovementController.cs:140`
- `Scripts/Character/AICharacterMovementController.cs:335`
- `Scripts/LevelGeneration/Area/AreaGenerator.cs:189,443`

Secondary smells inside it: `GetPlatformByGameObject` (`PlatformRegistry.cs:83–92`) does a `GetComponent` parent-walk plus LINQ `ContainsValue`/`FirstOrDefault` (O(n) with allocation) per query.

**Rule / cost.** §4 — "manual service locators are FORBIDDEN"; §14 — static manager / global state. The self-instantiation + `DontDestroyOnLoad` gives it a cross-scene lifetime nobody owns or resets except by convention (`Clear()` calls from `AreaGenerator`), a hidden-state hazard across Hub → run → arena scene flows.

**Fix.** Bind an `IPlatformRegistry` as a Zenject single (plain class — nothing in it needs `MonoBehaviour`); inject into the three consumers (the movement controllers already take `[Inject] IGameLogger`, so the seam exists). **Cost:** ~6 files + installer line; low risk. **Disposition:** ROADMAP; also unlocks F8's clean fix.

### F3 — P0 · Hero movement dual-path (two divergent controllers, both on `Hero.prefab`)

**What.** Two MonoBehaviours implement the *same job* — read player input, move with gravity, dash, jump platforms, maintain the current platform and fire `PlatformEvents`:

- `Scripts/Character/CharacterMovementController.cs` (327 lines, **live**);
- `Scripts/Character/AICharacterMovementController.cs` (436 lines, **dormant** — despite the "AI" name it reads player input, `AICharacterMovementController.cs:86`, and its own log tag says "[CharacterMovementController]", line 70).

They have already drifted: dash = raycast-vs-wall (`CharacterMovementController.cs:251–265`) vs polygon-edge intersection math (`AICharacterMovementController.cs:269–299`); neighbour-platform pick = angle < 90° (`CharacterMovementController.cs:278`) vs dot > 0.3 (`AICharacterMovementController.cs:223`). Meanwhile `UpdateCurrentPlatform` / `SetCurrentPlatform` / `MoveToPlatformInstant` are verbatim duplicates (`CharacterMovementController.cs:138–185` vs `AICharacterMovementController.cs:320–367`) — **both fire the global `PlatformEvents`**, the trigger for world streaming, autosave, loot spawn, and narrative windows.

`Resources/Prefabs/Hero.prefab` carries **both** components: the live one at line 202, the dormant one at lines 216–235 with `m_Enabled: 0` and no input actions wired.

**Rule / cost.** §14 duplication (the "Hub-as-parallel-world" class of bug: one re-enable or one copy-paste from the stale twin and the platform-transition semantics fork); §5 — both are business-logic-heavy MonoBehaviours (dash geometry, platform-graph navigation); §6 — input read directly in `Update` instead of the input seam; §1 — Russian comments (`CharacterMovementController.cs:217,228,242`); commented-out dead code (`CharacterMovementController.cs:95–103,320–325`).

**Fix.** (1) Delete the dormant twin + its prefab component — hand the liveness confirmation to **W3** (only reference found: the disabled `Hero.prefab` component). (2) Extract the live controller's movement/dash/platform-transition logic into a pure-C# model driven through the input abstraction, leaving a thin adapter — pairs naturally with the filed locomotion-polish item (P5-11). **Disposition:** step 1 fix-now-cheap (after W3 confirms); step 2 ROADMAP.

### F4 — P1 · `ArenaPlatformBuilder` re-implements `PlatformView`'s assembly

**What.** `Scripts/Combat/Arena/View/ArenaPlatformBuilder.cs:50–76` hand-assembles the platform scene object (mesh GO, `MeshFilter`/`MeshRenderer`/`MeshCollider`, wall colliders) — the exact job of `Platform/View/PlatformView.Initialize` (`PlatformView.cs:44–99`), whose own doc-comment (added by the O1 Hub reconvergence) declares that overload "the one place that logic lives". The arena copy predates/escaped that reconvergence.

**Drift already visible:** fallback material = `Shader.Find("Standard")` in `PlatformView.cs:83` (renders magenta under this URP project — a latent defect in its own right) vs `Universal Render Pipeline/Lit` in `ArenaPlatformBuilder.cs:68`. Arena platforms also skip the dressing/tone chain entirely, so any future look change lands only on world platforms.

**Fix.** Arena builds its root GO, then `AddComponent<PlatformView>()` + `SetConfig` + the `Initialize(surface, topBoundary)` overload — the same path the Hub took. **Cost:** 1–2 files, small; verify arena visuals once. Fix the `Standard`-shader fallback in `PlatformView.cs:83` in the same pass. **Disposition:** ROADMAP, cheap, precedent set by O1.

### F5 — P1 · `CombatActiveState` — 19-dependency god-seam

**What.** `Scripts/Platform/States/CombatActiveState.cs:29–48` — 19 constructor-injected dependencies; 663 lines; `OnEnter` (`:110–326`) orchestrates camera, input, character-combat init, enemy instantiation (`:386–501`), unit views, ability/status catalogs, loot drops, and dialogue in one method chain.

**Rule / cost.** §4 — "if a class has many dependencies, reconsider its responsibilities"; §14 god object. Concretely: this is the neighbourhood of the **D6** bug cluster (hero vs enemy vs crew resolving spawn/facing through divergent sub-paths) — the owner has already called for diagnose-and-unify there.

**Fix.** Extract the two heavy phases into their own collaborators: a combat-bootstrap composer (camera/input/UI wiring) and a single unit-spawn path (which is D6's requirement anyway). **Disposition:** fold the spawn-path half **into D6** (cite, don't duplicate); file the bootstrap extraction as its own ROADMAP row. Medium cost, PvE-only blast radius.

### F6 — P1 · Single runtime assembly — layering is convention-only

**What.** `Scripts/Yasherica.asmdef` is the only runtime asmdef (plus editor + tests). Not a big-bang: one system's Core per pass. **Disposition:** ROADMAP (enabler; makes F7-class violations impossible instead of audited).

### F8 — P1 · `ContentSpawner` resolves views by GameObject name

**What.** `Scripts/Platform/View/ContentSpawner.cs:160` — `GameObject.Find($"Platform_{platform.Id}")`, with a `FindObjectsByType<PlatformView>` name-matching fallback at `:167–175`. §5 explicitly forbids `GameObject.Find`. The platform→view mapping it needs **already exists** in `PlatformRegistry` (`platformToView`, `PlatformRegistry.cs:29`) but has no accessor — the in-code comment admits it (`ContentSpawner.cs:157–159`). The name-string contract also silently couples to `AreaGenerator.cs:402`'s naming.

Secondary: `UnityEngine.Random` for spawn placement (`ContentSpawner.cs:139,149–150`) — the one unseeded RNG in an otherwise deterministic world-gen chain (cosmetic-only today; noted for W4's determinism lens).

**Fix.** Add `GetView(IPlatform)` to the (post-F2, injected) registry; delete both lookups. **Disposition:** fix-now candidate — small, mechanical, removes a forbidden API.
