# W1 — Data-Driven / SO Extensibility Audit

**Pass:** Track W · W1 (brief: `product-requirements/architecture-and-extensibility-audit.md`)
**Date:** 2026-07-07 · **Scope:** every content-bearing subsystem, measured against CLAUDE.md §1 ("content is added by authoring ScriptableObjects, not by writing code") and §7 (SO usage rules).
**Read-only:** no code, asset, or doc changed — except one **erratum appended to `audits/W3.md`** (a W3 deletion candidate turned out to co-host a live enum; see F1).

**Method.** Full SO-type inventory (57 concrete types + 4 ability subclasses + 3 dressing-kit subclasses, all `[CreateAssetMenu]` paths extracted); per subsystem, the add-one-instance path traced from asset creation through its load channel (`Resources.LoadAll` auto-discovery vs installer `[SerializeField]` lists vs scene wiring) to the consuming system; mechanical hunts for hard-coded variety (switches/ladders over content kinds, literal content ids in logic, enum-keyed content); a logic-in-SO scan over all SO classes; a docs-coverage check of all 57 types against `Docs/*.md`.

## Headline

The data path is in **very good shape** — materially better than the CLAUDE.md-violation base rate elsewhere (cf. W2). Almost every content kind is add-one-asset with `LoadAll` auto-discovery, SOs hold **zero logic**, no literal-id ladders exist in logic, and 56 of 57 SO types are documented. **One real P0 gap exists: biome identity is a C# enum** — the single place a designer must edit code to add content.

## Findings

### F1 — P0 · Biome identity is a C# enum (`LevelTheme`) — the one designer-must-touch-code path

**What.** Every biome-keyed SO carries a `LevelTheme` enum field: `BiomeAppearanceDefinition.cs:21`, `BiomeLootDefinition.cs:14`, `BiomeMonsterPoolDefinition.cs:16`, `RaceDefinition.cs:23` (`_homeBiome`); the enum itself is `LevelTheme { Forest, Desert, Mountain, Cave, Hub }` at `ScenarioData.cs:108`, referenced by **45 files**. Adding a biome therefore requires a **code edit** (the enum) before any asset can even name it — a direct §1 break ("new content … is added by authoring ScriptableObjects, not by writing code"; a gap here is exactly what §1 says to record).

**Mitigating reality.** There are **no `switch`/`case` ladders over `LevelTheme` anywhere** — all consumers do data lookups (catalogs keyed by theme), so the enum is *pure identity*, which is precisely why it can be replaced by data cheaply. The Hub entry even documents the exclusion-by-data convention (`ScenarioData.cs:115–117`).

**Aggravating reality.** The enum lives inside `ScenarioData.cs` — a file **W3 lists as confirmed-dead** (the `ScenarioData` class is; the enum is not). A wholesale file deletion would break 45 files. An erratum was appended to `audits/W3.md` §1.2-D.

**Fix shape.** Introduce a `BiomeDefinition` SO (id + display data) as the identity, migrate the four SO fields from `LevelTheme` to a biome-id reference (the `[RaceId]`-drawer pattern already shows the project's own way to keep authoring ergonomic), keep `LevelTheme` as a compatibility alias during migration. **Cost:** medium — ~45 files reference the type but almost all just pass it through; the four SO field migrations need asset re-saves. **Disposition:** ROADMAP (P0 by the rubric; practically: schedule before the "real Mtn/Desert rosters" follow-up lands more biome content on the enum).

### F2 — P1 · `AIProfileDefinition` is documented nowhere

The docs-coverage sweep (all 57 SO types × all `Docs/*.md`): **56 covered, one miss** — `AIProfileDefinition` (`Scripts/Combat/Data/Definitions/AIProfileDefinition.cs`, menu `Combat/AI/AI Profile`, one instance: `Resources/Enemies/AIProfiles/TestAIProfile.asset`, GUID-referenced by three enemy definitions). §7: "a new SO type without doc coverage is an incomplete change." It predates the doc discipline. **Fix:** add it to the combat/enemy system doc's SO Reference + an add-recipe (which doc owns enemy AI is the owner's call — likely `ability-subsystem.md` or a future combat-AI doc with P2-4). Worklist → W5.

### F3 — P2 · The inspector-list-else-`LoadAll` hybrid is a latent trap

`InventoryInstaller.cs:237–256`, `CharacterSystemInstaller.cs:101`, `AreaInstaller.cs:539–548` (and the hero at `AreaInstaller.cs:508–520`) all use: *if the scene's `[SerializeField]` list is non-empty, use it **exclusively**; else `LoadAll`*. Today every shipped list is empty, so auto-discovery works and add-one-asset holds. But the day someone populates a list in a scene (e.g. to test a subset), **every asset added to `Resources/` afterwards is silently ignored** for that scene — the classic "my artifact doesn't show up" trap with no error. **Fix options:** delete the inspector override entirely (Resources is the contract), or log a prominent warning when the override path wins. One-file-each, trivial.

### F4 — cited, not re-filed · Reward payload kinds are a closed enum

`QuestRewardPayloadKind { Artifact, PartBlank }` (`QuestRewardPayloadKind.cs:8–15`) + the kind-routing granter: a new non-item reward kind (Currency/Experience/Ability) is a code change — **already filed as P1-12** and deliberately deferred until a currency model exists (owner 2026-07-05). Nothing new to add; noted here only because the touch-count table must show it.

### F5 — P2 (accepted seam) · New ability *kind* = subclass + factory case

`AbilityFactory.CreateAbility` (`AbilityFactory.cs:24–31`) pattern-matches over the four `AbilityDefinition` subclasses. Adding an ability **instance** is one asset ✓; adding a **kind** (a new behaviour shape) is a subclass + one factory case. That is a reasonable Strategy-factory seam — a kind *is* behaviour — but it is the ability system's variety boundary and should be stated in `ability-subsystem.md`'s Adding-Content section so a designer knows where asset-authoring ends. (Check whether it already is → W5 worklist.)

### F6 — P2 · Bark slots are an enum

`CauldronBarkSlot` (`Scripts/Narrative/Barks/Core/CauldronBarkSlot.cs`) — bark *lines* per slot are data (`CauldronBarkLinesConfig`) ✓, but a new bark **moment** (slot) is an enum member + a firing call site. Fine for now (slots are engine moments, like site base kinds); worth a doc sentence, and if slots multiply, consider string slot ids.

### F7 — hand-back to W3 · A second dead lane found

`IAbilityDataProvider` + `ScriptableObjectAbilityProvider` (`Scripts/Combat/Data/Providers/`): bound **only** conditionally when the (always-empty) `_abilityDefinitions` scene list is populated (`AreaInstaller.cs:527–533`), and **no production class injects `IAbilityDataProvider` at all** — the live path is `IAbilityDefinitionCatalog` (`LoadAll`). Production-dead lane; also the "second data source" instance of the F3 hybrid. → add to W3's Wave-3 list.

### F8 — observation (→ W1/W5 border) · SO types with zero instances

From W3, restated as authoring-surface facts: `HealAbilityDefinition` (live factory branch `AbilityFactory.cs:28`, zero assets — no heal ability has ever been authored) and `RunPacingConfig` (installer maps `null` → code defaults, `NarrativeSliceInstaller.cs:202–203` — pacing is effectively hard-coded until someone creates the asset; worth creating one so tuning is data as intended). Neither is a violation; both are unused designer surfaces.

## Checked and clean (state it, since this audit's job is measurement)

- **SOs hold zero logic.** Method scan across all 57 SO types: the big content SOs (`ArtifactDefinition`, `StoryTemplate`, `EnemyDefinition`, `PartDefinition`, `PartBlankDefinition`, `QuestDefinition`, `BiomeAppearanceDefinition`, …) have **0 methods**; the only hits are single expression-bodied property getters. §7 fully respected.
- **No literal content-id ladders.** The only content ids in production code are two demo facts in the **curated typed mirror** `WorldFacts` (`TypedFacts.cs:11–12` — the class itself documents "source of truth remains the SO registry"), plus engine facts (`run_count`, `run_escalation_tier`, spine cursors) that code rightfully owns. No `if (id == "…")` logic anywhere.
- **The mapper rule (§7) holds.** Spot-checked the Data→Core bridges (`DefinitionMapper`, `DressingKitMapper`, `SiteCatalogMapper`, `RaceRosterMapper`, `HubVoiceLinesMapper`, `BiomeMonsterPoolMapper`): Core records are Unity-free — e.g. `PartData` (`CharacterSystem/Core/PartData.cs`) carries **no** Mesh/GameObject/Material. (The `Combat/Core` UnityEngine exceptions are W2 F7 — cited, not re-filed.)
- **Load channels are auto-discovering.** Narrative (stories/actors/dialogues/facts/quests/threads), world (races/sites/biomes/dressing), combat (abilities/status-effects/monster-pools/enemies), mutation, loot — all `Resources.LoadAll` folder conventions; adding an asset to the folder is sufficient (modulo F3's latent override).
- **Doc coverage 56/57** SO types mentioned in `Docs/` (F2 is the miss); 26 docs carry Adding-Content sections. Whether each mention is a *complete* field-table + recipe is W5's per-doc drift check, not re-done here.
- **Authoring ergonomics exist**: `[RaceId]` data-driven drop-down (`RaceIdDrawer.cs`), the `/part-spec`, `/content-graph`, `/balance-ledger` integrity tools (per brief rule 9, their domains were not re-derived).
